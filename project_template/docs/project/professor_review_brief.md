# 무장애·가족 친화 관광 챗봇 시제품 검토 자료

마지막 갱신: 2026-05-18

## 1. 검토 목적

검토받고 싶은 핵심은 무장애 관광 추천 문제를 풀기 위해 TourAPI/RAG/fallback, 자연어 처리, ML 보조 분류기, 실제 chat 평가를 어떻게 결합했는지다. 제품 범위는 관광 추천에 한정하고, 의료·예약·실시간 정보는 제외한다.

## 2. 한 줄 요약

> 한국관광공사 무장애 여행 정보와 로컬 RAG/fallback 자료를 결합해, 지역·접근성 조건을 이해하고 근거가 있는 관광지 카드를 추천하는 상담형 시제품이다.

단순히 LLM을 붙인 챗봇이 아니라, 자연어 의도와 대화 문맥을 따로 분석하고 그 결과를 추천 품질 평가에 연결했다는 점을 확인받기 위한 자료다.

## 4. 기술 구조

| 요소 | 역할 |
|---|---|
| FastAPI | `/tourism/chat`, `/tourism-ui/`, 상태 확인 API 제공 |
| TourAPI | 한국관광공사 무장애 여행 정보 후보와 상세 접근성 정보 조회 |
| 로컬 fallback | API 실패·쿼터·네트워크 불안 시에도 응답 가능한 Markdown 카드 |
| ChromaDB/RAG | 저장된 관광 카드와 문서를 검색해 후보 근거 확보 |
| 규칙 파서 | 지역, 조건, 제외, 더 보기, 최신 조회, 미지원 요청 처리의 1차 기준 |
| ML 보조 분류기 | 의도/문맥 판단 보조. 규칙을 대체하지 않고 헷갈리는 표현을 확인 |
| 로컬 한국어 교정 모델 | 오타·무띄어쓰기·축약어 입력을 후보 문장으로 보정 |
| LLM 추론 보조 | 기본 OFF. 켜도 후보 생성이 아니라 카드 재랭킹/확인 메모 보조로 제한 |

응답 흐름:

```text
질문
-> 지역/조건/후속 의도 해석
-> 모호 지역이면 선택 질문
-> cache / RAG / fallback 후보 확인
-> 부족하거나 사용자가 요청하면 live TourAPI 보강
-> 조건 근거가 있는 카드만 추천
-> 출처, 주의 문구, 후속 제안 반환
```

## 5. 사용자 경험

시연 화면은 `/tourism-ui/`다.

- 개발 모드와 릴리즈 모드를 분리했다. 릴리즈 모드에서는 내부 진단을 숨긴다.
- 추천 카드는 접근성 근거, 상세 정보, 지도 검색으로 확인할 수 있다.
- 브라우저 세션별 `session_id`를 유지해 `더 보기`, 조건 변경, 지역 변경 같은 후속 질문을 이어받는다.

## 7. 자연어 처리와 ML 활용

질문을 그대로 LLM에 넘기지 않고, 먼저 아래 정보를 분리해 처리한다.

- 사용자가 원하는 행동: 추천, 더 보기, 조건 변경, 제외, 최신 조회 등
- 이어받을 대화 조건: 지역, 접근성 조건, 가족/이동 편의, 제외 선호
- 추천 제어 방식: 규칙 기반 처리를 중심으로 두고, ML은 보조 신호로 사용
- 평가 방식: 라벨 점수와 실제 chat 카드 품질을 분리해 확인

### 7.1 의도 분류

- 목적: 사용자의 다음 행동을 분류한다.
- 대상: `추천`, `더 보기`, `최신 정보`, `조건 추가`, `조건 교체`, `조건 제외`, `지역 변경`, `미지원 요청`.
- 데이터: 자체 발화, AI Hub 관광 대화 추출 발화, 경계 사례, 실제 chat 평가셋.
- 현재 적용: 규칙 기반 처리가 주도하고, 문자 n-gram Naive Bayes는 보조 신호로 사용한다.
- 예시: `오늘 환율 알려줘`는 비관광 요청으로 차단한다.
- 예시: `응급실은 말고 관광지만 계속`은 부정 표현을 보고 관광 문맥을 유지한다.

| 항목 | 지표 | 결과 |
|---|---|---:|
| 의도 분류 학습셋 | 학습 row 수 | 16,254 rows |
| 내부 holdout | accuracy | 0.9164 |
| AI Hub/adversarial holdout | accuracy | 0.9229 |
| Gemini verified holdout | accuracy | 0.8536 |
| 실제 chat holdout | 자동 채점 통과율 | 243/243 |

### 7.2 문맥 해석

- 목적: 추천 결과를 바꾸는 조건 해석을 분리한다.
- strict 조건: `둘 다`, `반드시`처럼 모든 조건이 필요한 요청.
- soft 조건: `가능하면`, `있으면 좋고`처럼 완화 가능한 요청.
- OR 조건: `수어 또는 자막`처럼 둘 중 하나면 되는 요청.
- 조건 교체: `유모차 말고 휠체어`처럼 기존 조건을 바꾸는 요청.
- 조건 제외: `시장 말고`, `카페 제외`처럼 빼야 하는 선호.
- 시설 근거: 휠체어, 유모차, 수유실, 점자블록, 가족 편의처럼 카드 근거가 필요한 요청.

비교한 접근은 rule-only, Naive Bayes, LinearSVC, LogisticRegression, hybrid 선형 모델, KLUE-RoBERTa small, SuperGemma4 selective labeling이다.

| 평가 | 결과 |
|---|---:|
| context locked test 최신 | micro-F1 0.9803 |
| independent validation 최신 | micro-F1 0.9741 |
| specific-facility adversarial | micro-F1 0.9946 |
| rotating blind v4 rule-only | micro-F1 0.9091 |
| rotating blind v4 hybrid LinearSVC | micro-F1 0.9012 |
| rotating blind v4 hybrid LogisticRegression | micro-F1 0.8968 |
| 실제 chat blind v2 | 15/15 통과 |

v4는 새 평가셋 기준의 일반화 확인용이다. 이 평가에서는 rule-only가 hybrid LinearSVC/LogisticRegression보다 조금 높았다. 따라서 현재 런타임은 복합 ML 모델로 교체하지 않고, 규칙 기반 처리를 중심에 두며 ML은 보조 신호로 유지한다.

### 7.3 Transformer와 LLM 채택 판단

- KLUE-RoBERTa small fine-tuning은 validation micro-F1 0.9241, locked test 단독 micro-F1 0.8594였다.
- rule hybrid micro-F1 0.9474보다 낮고 응답 지연도 길어 런타임 교체는 보류했다.
- SuperGemma4 selective labeling은 일부 exact를 올렸지만 micro-F1이 하락해 QA/재라벨링 보조로만 둔다.
- 결론: 현재 구조는 **규칙 기반 처리 + ML 보조 신호 + 실제 chat 평가** 조합이다.
- LLM은 후보 생성 엔진이 아니라, 필요할 때 카드 순서와 설명을 보조하는 역할로 제한한다.

### 7.4 오타·띄어쓰기 보강

일반 사용자는 `휄체어`, `엘베`, `부산중구휠체어화장실`처럼 오타와 무띄어쓰기 입력을 넣을 수 있다. 이를 위해 한국어 교정 모델을 외부 API가 아니라 로컬 파일로 내려받아 프로젝트 데이터로 추가 학습했다. FastAPI는 Hugging Face에 접속하지 않고 로컬 모델만 읽는다.

교정 결과는 원문을 대체하지 않는다. 원문, 도메인 정규화문, 교정 후보문을 병렬로 해석하고, 보호어와 지명이 훼손되면 교정 후보를 버린다. quickspacer도 띄어쓰기 전용 후보로 검토했지만 `수어자막`을 잘못 쪼개는 사례가 있어 전역 적용하지 않는다.

| 비교 | 결과 |
|---|---:|
| 교정 모델 validation exact accuracy | 0.7124 |
| 교정 모델 validation compact accuracy | 0.7521 |
| 핵심어 5,000건 수동/도메인 정규화 exact | 0.8596 |
| 핵심어 5,000건 로컬 교정 병행 exact | 0.8598 |
| 교정 병행 개선/회귀 | 개선 1건 / 회귀 0건 |
| 중간 길이 chat v3 직접 평가 | 18/20 통과 |

현재 교정 모델은 한국어 전체를 고치는 범용 모델이 아니라, 무장애 관광 질의를 파서가 읽기 쉽게 만드는 후보 레이어다. 문자 n-gram과 부분문자열 기반 규칙은 무띄어쓰기 입력에 강하므로, 띄어쓰기 모델이 항상 더 좋은 것은 아니다.

### 7.5 현재 런타임에서 쓰는 방식

현재 챗봇은 룰셋만으로 동작하지 않는다. 다만 최종 행동 결정의 중심은 규칙 기반 처리이고, ML과 RAG는 아래 위치에서 보조한다.

| 구성 | 실제 역할 |
|---|---|
| 규칙 파서 | 지역, 조건, 제외, 교체, 더 보기, 최신 조회, 미지원 요청을 1차 판단 |
| 도메인 정규화 | 자주 나오는 오타, 축약어, 지명/시설명 띄어쓰기 흔들림을 보정 |
| 로컬 교정 모델 | 위험 신호가 있는 문장만 후보 교정. 원문 대체는 하지 않음 |
| 의도 분류기 | 문자 n-gram Naive Bayes. 짧은 후속 발화가 어떤 행동인지 보조 판단 |
| 문맥 라벨 분류기 | strict/soft/OR/교체/제외/가족/이동/시설 근거 라벨을 보조 판단 |
| RAG/Chroma 검색 | 저장된 관광 카드와 문서에서 후보를 찾고 추천 근거 확보 |
| TourAPI/로컬 카드 | 휠체어, 주차, 화장실, 수유실, 점자블록 등 접근성 근거 확인 |
| LLM | 기본 OFF. 켜도 후보 생성이 아니라 재랭킹, 설명, 검수 보조로 제한 |

따라서 현재 구조는 **룰셋 단독**이 아니라, **규칙 기반 제어 + ML 보조 신호 + RAG/구조화 데이터 근거 확인** 조합이다. 한국어의 우회 표현과 생략은 실제 사용자 발화와 LLM 생성 발화로 라벨을 확장하고, 이후 룰셋 함수 또는 Transformer 계열 분류기로 고정하는 방향이 필요하다.

### 7.6 진행 중인 추가 검증

중간 길이 실제 질의 평가셋을 별도로 만들었다. 또한 조건 라벨 Transformer 학습 데이터를 새로 구성해 기존 핵심어 5,000건에 지역, 장소 유형, 말투, 오타, 무띄어쓰기 증강 10,000건을 더했다.

`klue/roberta-small`은 Hugging Face에서 실시간 호출하지 않고, 로컬 `data/models/klue_roberta_small/`로 내려받아 로컬 학습 경로에서만 사용한다. 2 epoch 조건 라벨 실험은 synthetic test micro-F1 0.9941로 높았지만, 증강 데이터 기반 결과라 런타임 채택 근거로 바로 쓰지 않는다. 실제 chat 카드 품질 개선을 별도로 확인한 뒤 보조 모델로만 검토한다.

quickspacer는 500건 샘플 비교에서 수동/도메인 정규화 exact 0.838, quickspacer 병행 exact 0.832로 낮았다. 일부 무띄어쓰기 문장은 개선했지만 `바퀴의자`, `이동약자`, `수어자막` 같은 보호 표현을 잘못 쪼갤 수 있어 현재 런타임에는 적용하지 않는다.

## 8. 시연에서 강조할 차별점

1. **근거 기반 카드 추천**: 휠체어·주차·화장실·수유실·점자블록 등 확인된 근거를 카드에 붙인다.
2. **지역 오인 방지**: `중구`처럼 여러 지역에 있는 이름은 바로 추천하지 않고 선택 질문을 한다.
3. **좁은 지역 자동 확장 금지**: 시군구를 명시하면 다른 지역을 임의로 섞지 않는다.
4. **후속 질문 처리**: `더 보기`, 조건 제외, 조건 교체, 지역 변경 흐름을 유지한다.
5. **환각 억제**: 근거가 없으면 카드를 만들지 않고 조건 완화나 지역 확장을 제안한다.
6. **검증 가능한 ML/NLP 개선**: 의도 분류, 문맥 라벨, 새 평가셋, 실제 chat 평가를 분리했다.
7. **시연 안정성**: live API가 불안해도 fallback/RAG로 기본 시연이 가능하다.
